# YouthLink 정책 Chunk 생성 전략

작성 기준: 2026-10-11  
Chunker 버전: `policy-v1`

## 1. 목적

`policy`의 정형·비정형 데이터를 검색에 적합한 의미 단위 텍스트로 변환하여 `policy_chunk`에 저장합니다. 이번 단계는 청크 텍스트 생성까지를 다루며, 임베딩 생성은 별도 파이프라인에서 수행합니다.

## 2. 실제 데이터 분석 결과

2026-10-11 검증 대상은 현재 로컬 DB의 정책 3,263건입니다. 최신 API 실행에서 처리한 3,238건과 이전 실행에서만 존재하던 25건을 포함합니다. 원천에서 사라진 정책의 비활성화는 아직 구현되지 않았습니다.

| 항목 | 결과 |
| --- | ---: |
| 정책 | 3,263건 |
| 정책-지역 관계 | 194,016건 |
| 자격 조건 관계 | 14,134건 |
| 미해결 지역코드 | 0건 |
| 이름이 없는 자격 코드 | 0건 |

신청 관련 텍스트와 URL이 모두 없어 `APPLICATION` 청크를 생략한 정책은 185건입니다.

지역명을 그대로 나열하면 `ELIGIBILITY` 청크의 95% 길이가 3,116자까지 증가합니다. 전국·시도 전체 압축을 적용하면 95% 길이는 529자, 최대 길이는 2,154자로 감소합니다.

## 3. Chunk 계약

정책별로 최대 네 개의 청크를 생성합니다. 인덱스는 고정하며 비어 있는 청크를 생략해도 다른 청크의 인덱스를 당기지 않습니다.

| `chunk_index` | `chunk_type` | 주요 내용 |
| ---: | --- | --- |
| 0 | `SUMMARY` | 정책명, 설명, 키워드, 분류, 기관 |
| 1 | `ELIGIBILITY` | 지역, 나이, 혼인, 소득, 전공·직업·학력·특화 조건, 추가 자격, 제외 대상 |
| 2 | `SUPPORT` | 지원 내용, 규모, 선착순, 제공 방식, 사업 기간, 기타 안내 |
| 3 | `APPLICATION` | 신청 기간, 신청 방법, 심사 방법, 제출 서류 |

`SUMMARY`는 항상 생성합니다. 나머지 종류는 정책명 외에 해당 섹션의 실질적인 내용이 있을 때 생성합니다. 실제 기간·방법·심사·서류가 없더라도 신청·참고 URL이 있으면 신청 경로가 존재하는 정책으로 판단해 기간 구분을 담은 `APPLICATION`을 생성하되, URL 문자열 자체는 임베딩 텍스트에서 제외합니다. 현재 로컬 데이터에서는 185건의 `APPLICATION`을 생략하여 총 12,867개 청크가 생성됩니다.

모든 청크에 정책명을 포함하여 청크 하나만 검색되어도 어떤 정책인지 알 수 있게 합니다.

## 4. 지역 표현

지역은 원본 `policy_region.region_code`가 아니라 `v_policy_region_resolved`의 현재 코드와 이름을 사용합니다. 이 View에는 과거 코드 매핑뿐 아니라 검증된 인천 9개 코드 범위 누락의 `INFERRED` 보정도 포함됩니다.

1. 현재 활성 지역 256개를 모두 포함하면 `전국`으로 표현합니다.
2. 특정 시도의 활성 시군구를 모두 포함하면 `{시도명} 전체`로 표현합니다.
3. 일부만 포함하면 중복을 제거한 현재 지역명을 코드 순서로 나열합니다.
4. `UNRESOLVED`와 비활성 지역은 청크 생성 대상에서 제외하고 별도 운영 점검 대상으로 둡니다.

백엔드와 RAG가 같은 범위 판정을 재사용할 수 있도록 DB는 정책 단위 `v_policy_region_scope`와 정책·시도 단위 `v_policy_sido_scope`도 제공합니다. 청크 생성기의 압축 결과는 이 View와 동일한 활성 `region` 집합을 기준으로 합니다.

예:

```text
적용 지역: 전국
```

```text
적용 지역: 서울특별시 전체, 경기도 수원시 장안구, 경기도 성남시 분당구
```

지역 마스터나 매핑이 바뀌면 렌더링 결과와 `content_hash`도 바뀌므로 해당 정책은 다시 임베딩해야 합니다.

## 5. 코드 이름

전공·직업·학력·특화 조건과 정책의 기간·혼인·소득·제공 방식 코드는 `common_code.code_name`으로 변환합니다. 이름이 없는 신규 코드는 수집을 중단하지 않고 원본 코드값을 대체 표시값으로 사용합니다.

## 6. 텍스트 정제

- `CRLF`, `CR`을 `LF`로 통일합니다.
- API 문자열의 리터럴 `\\N`을 실제 줄바꿈으로 변환합니다.
- BOM과 zero-width space를 제거합니다.
- 각 줄의 앞뒤 공백을 제거하고 연속 빈 줄을 하나로 줄입니다.
- `<생애최초>`, `<서식 1>`, `<예정>`처럼 의미가 있는 꺾쇠 표현을 보존합니다.
- URL은 임베딩 텍스트에서 제외하고 검색된 `policy`의 메타데이터로 제공합니다.

## 7. 결정성과 변경 감지

- 지역과 코드 목록은 항상 고정된 코드 순서로 정렬합니다.
- 동일한 DB 상태에서는 동일한 `content`가 생성되어야 합니다.
- `content_hash`는 UTF-8 `content`의 SHA-256 소문자 hex 값입니다.
- 생성기 버전은 `policy-v1`입니다.
- 내용 또는 생성기 버전이 바뀐 청크만 갱신하며 기존 임베딩을 무효화합니다.
- 변경되지 않은 청크는 `chunk_id`, `updated_at`, 임베딩을 유지합니다.
- 새 결과에서 사라진 청크는 정책 단위 동기화 시 삭제합니다.

## 8. 임베딩 상태 규칙

아직 임베딩되지 않은 청크는 다음 상태입니다.

```text
embedding = NULL
embedding_model = NULL
embedded_at = NULL
token_count = NULL
```

임베딩 성공 후에는 벡터, 모델명, 토큰 수, 생성 시각을 함께 기록합니다. 청크 내용이 변경되면 이 값들을 다시 `NULL`로 만들고 다음 임베딩 실행 대상으로 둡니다.

## 9. 검색 결과 처리

동일 정책의 여러 청크가 검색될 수 있으므로 최종 후보는 `policy_no` 단위로 묶습니다. 정책명이 같아도 연도·지역·운영기관이 다른 정책일 수 있으므로 정책명만으로 중복 제거하지 않습니다.

## 10. 실행 단계

```text
정책·지역·코드 데이터 조회
→ policy-v1 텍스트 렌더링
→ content_hash 비교
→ 신규·변경 청크 UPSERT
→ 사라진 청크 삭제
→ 변경 청크의 임베딩 무효화
```

임베딩 API 호출과 pgvector 검색은 별도의 `etl/embed_policy_chunks.py`, `etl/search_policy_chunks.py`가 담당합니다. 실행 방법은 [임베딩 및 pgvector 검색 파이프라인](embedding-pipeline.md)을 참고합니다.
